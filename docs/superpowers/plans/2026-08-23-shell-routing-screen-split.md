# Shell, Routing and the Screen Split (PR 3b) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the app a content width cap, real URLs, and a sidebar shell, then move ~1302 lines of JSX out of `src/ui/EcuLab.jsx` into one file per screen — **without changing what is on which screen.**

**Architecture:** A pure route module parsed from `location.hash`, an `AppShell` that owns the sidebar and status strip, and one screen file per existing section. Screens read domain state from the store hooks the last PR built; only navigation state changes shape.

**Tech Stack:** React 18, CSS Modules, Vitest + @testing-library/react, JSDoc types checked by `tsc --checkJs`. **No new dependencies** — the routing is ~40 lines, not a router.

## Route shape

```
#/                    start screen
#/tutorial            tutorial
#/dash                DASH, all accordions closed
#/dash/live           DASH, live section open
#/build/engine        BUILD, engine section open
#/tune/spark          TUNE, spark view
#/dyno/result         DYNO, result view
```

Three things this has to get right, and each has a wrong answer that looks fine:

1. **`appView` disappears into the route.** `#/` is the start screen, `#/tutorial` is the tutorial, anything else is the app. There is no separate `appView` state afterwards.
2. **The accordions' "all closed" state is real.** `buildSection` and `dashSection` are `null` when everything is collapsed, and that is reachable today by clicking an open section's header. `#/dash` with no segment **is** that state — do not invent a `none` sentinel, and do not let `null` fall back to a default section, which would make a section impossible to close.
3. **An unknown route must not render a blank screen.** `#/tune/nonsense` should land somewhere sensible and say so in the URL. Decide the rule, write it down, and test it.

### Task 1: The content width cap

**Files:**
- Modify: `src/ui/EcuLab.jsx`, `src/ui/tokens.css`
- Test: `tests/tokens.test.js`

**This goes first, alone, because it is the one change in the PR a human can eyeball in ten seconds** — and because it is the actual root of the complaint that started the overhaul. Nothing sets a `max-width` today, so every container *is* the viewport, and `Button`'s `block` prop consequently ships with zero adopters.

- [ ] **Step 1: Add the token**

`tokens.css` and `tokens.js` are under a bidirectional contract test (`tests/tokens.test.js`), so a token added to one must be added to the other with the same value. Add:

```
--content-max: 1100px;   /* contentMax: '1100px' in tokens.js */
```

**Why 1100.** The widest fixed element is the tuning grid at 452px, so the grid is not the constraint — prose is. The explainer paragraphs run at `--fs-base` 13.5px, where 1100px of column is roughly 110 characters: past the comfortable 45-90 but acceptable for a dense tool, and it leaves room for #83's right-hand panel beside a 452px grid (452 + ~320 + gaps ≈ 820) without a second breakpoint. If you disagree after seeing it, say so with a number and a reason — this is a judgement, not a measurement.

- [ ] **Step 2: Apply it to the content column, not the shell**

The root at `EcuLab.jsx:1059` is `height: 100dvh` with `overflow: hidden`. **Cap the scrolling content column inside it, not the root** — capping the root would letterbox the whole app including the future sidebar, and would make the status strip stop short of the screen edge.

- [ ] **Step 3: Prove the cap exists and is bound to the token**

Add to `tests/tokens.test.js`:

```js
it('caps the content column so it cannot span an unbounded display', () => {
  // The app had no max-width anywhere: the root is 100dvh tall with unconstrained
  // width, so every container was the viewport. That is why buttons spanned the
  // screen, and why Button's `block` prop shipped with no adopters.
  expect(tokens.contentMax).toMatch(/^\d+px$/);
  expect(Number.parseInt(tokens.contentMax, 10)).toBeLessThan(1600);
});
```

That pins the token. **It does not pin that anything uses it** — check whether a test can assert the content column actually references `var(--content-max)`, and if you can make one that bites, add it. If you cannot, say so rather than leaving the weaker test looking like coverage.

- [ ] **Step 4: Verify and commit**

```bash
npx vitest run tests/tokens.test.js tests/ui/ --pool=forks --poolOptions.forks.singleFork
npm run lint
npm run typecheck
```

**Interfaces:**

- [ ] **Step 1: Write the failing tests**

Create `tests/ui/routing.test.js`:

```js
import { describe, expect, it } from 'vitest';

import { formatRoute, parseRoute } from '../../src/ui/routing.js';

describe('parseRoute', () => {
  it('reads the empty hash as the start screen', () => {
    expect(parseRoute('')).toEqual({ view: 'start', tab: null, section: null });
    expect(parseRoute('#/')).toEqual({ view: 'start', tab: null, section: null });
  });

  it('reads a tab with no section as that tab with everything collapsed', () => {
    // `null` is a real, reachable state: clicking an open accordion's own header
    // closes it. A default section here would make a section impossible to close.
    expect(parseRoute('#/dash')).toEqual({ view: 'app', tab: 'dash', section: null });
  });

  it('reads a tab and section', () => {
    expect(parseRoute('#/tune/timing')).toEqual({ view: 'app', tab: 'tune', section: 'timing' });
  });

  it('falls back for an unknown tab rather than rendering nothing', () => {
    expect(parseRoute('#/nonsense')).toEqual({ view: 'start', tab: null, section: null });
  });

  it('drops an unknown section but keeps the tab it belongs to', () => {
    // A stale deep link to a renamed screen should land on that tab, not a blank page.
    expect(parseRoute('#/tune/nonsense')).toEqual({ view: 'app', tab: 'tune', section: null });
  });

  it('ignores a trailing slash and surplus segments', () => {
    expect(parseRoute('#/build/engine/')).toEqual({ view: 'app', tab: 'build', section: 'engine' });
    expect(parseRoute('#/build/engine/extra')).toEqual({ view: 'app', tab: 'build', section: 'engine' });
  });
});

describe('formatRoute', () => {
  it('round-trips every valid route', () => {
    // Derived from ROUTES rather than a hand-written list, so a screen added later is
    // covered the day it appears.
    const cases = [
      { view: 'start', tab: null, section: null },
      { view: 'tutorial', tab: null, section: null },
      { view: 'app', tab: 'dash', section: null },
      { view: 'app', tab: 'tune', section: 'timing' },
    ];
    cases.forEach((route) => {
      expect(parseRoute(formatRoute(route))).toEqual(route);
    });
  });
});
```

### Task 3: Wire the route to the existing view state

**Files:**
- Create: `src/ui/useRoute.js`
- Modify: `src/ui/EcuLab.jsx`

**The markup does not move in this task.** Six `useState` calls become one route, the URL starts reflecting where you are, and every screen still renders from exactly where it does today. That ordering means each later extraction is verifiable against a URL that already works.

- [ ] **Step 1: The hook**

`useRoute()` subscribes to `hashchange`, returns the parsed route, and exposes a `navigate(route)` that sets `location.hash`. Two things to get right:

- **Read the hash once on mount**, so a deep link works on a cold load rather than only after a navigation.
- **`navigate` must not push a duplicate entry** when the target equals the current route, or the back button gathers dead steps that appear to do nothing.

- [ ] **Step 2: Replace the six `useState` calls**

`appView`, `tab`, `buildSection`, `tuneView`, `dynoView`, `dashSection` all come from the route. `ExpandableInfo`'s `open` stays — it is per-instance disclosure state, not navigation.

**Watch the accordion toggles.** Today they read `active={buildSection === 'engine'}` and set `buildSection === 'engine' ? null : 'engine'`. That "click the open one to close it" behaviour must survive — it is the `null` state, and it is the one thing about this conversion most likely to be lost quietly.

They navigate by clicking real controls, so they exercise the routing without knowing it exists. **If one fails, the wiring is wrong.** Do not edit them.

- [ ] **Step 4: Add what the characterisation tests cannot see**
